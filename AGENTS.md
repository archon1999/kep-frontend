# Agent Instructions

## Scope

This file applies only to `kep-frontend/`.
Ignore sibling projects such as `kep-backend/`, `Aurora/`, and `angular-frontend/`
unless a task explicitly depends on them.

## Project Context

1. This frontend is built with Vite, React 19, TypeScript, MUI 7, React Router 7,
   SWR, Axios, and i18next.
2. `src/app` owns the app shell: router, layouts, providers, theme, locale config,
   and global wiring.
3. `src/modules` owns feature work.
4. `src/shared` owns code reused across multiple modules or by the app shell.
5. OpenAPI client code is generated by Orval into `src/shared/api/orval`.
6. The checked-in `README.md` is still scaffold boilerplate. Treat the source tree
   and config files as the source of truth.

## Module Architecture Standard

For every folder under `src/modules/*`, the target internal architecture must match
this structure exactly unless an explicit, approved exception is documented.

```text
src/modules/<module-name>/
  index.ts

  application/
    index.ts
    keys.ts
    queries.ts
    mutations.ts

  data-access/
    index.ts
    repository/
      <module>.repository.impl.ts
    mappers/
      index.ts
      *.mapper.ts
    mocks/                       # optional

  domain/
    index.ts
    contracts/
      index.ts
      <module>.repository.ts
    entities/
      index.ts
      *.types.ts
    enums/
      index.ts
      *.enums.ts
    utils/                       # optional, pure domain helpers

  ui/
    index.ts
    pages/
      <PageName>/
        <PageName>.tsx
        components/
        dialogs/
        widgets/
    shared/                      # module-local reusable ui/helpers
      index.ts
      components/
      helpers/
```

Some existing modules in this repository currently diverge from this shape.
Treat the structure above as the required target state for new work and future refactors.

## App and Shared Structure

Outside feature modules, keep using the current repo layout:

```text
src/
  app/                          # router, layouts, providers, theme, locales, app config
  assets/                       # app-level static assets
  modules/                      # feature modules, following the standard above
  shared/                       # cross-module and app-wide code
types/                          # ambient types and declarations
```

## Layer Responsibilities

### `src/app`

1. Keep global composition here: router, layouts, providers, theme, locale, and shell.
2. Route changes should update `src/app/routes/resources.ts`.
3. Top-level route wiring belongs in `src/app/routes/router.tsx`.
4. If a route changes the main navigation, also update `src/app/routes/sitemap.ts`.
5. Do not move feature-specific business logic into `app/`.
6. Do not reorder providers in `src/main.tsx` lightly. Provider order affects theme,
   locale, settings, and SWR behavior.

### `domain/`

1. Define business entities and repository ports.
2. No React, MUI, SWR, Axios, or browser side effects.
3. Do not expose raw backend DTO shapes as domain models.
4. Inside modules, prefer `domain/contracts` as the repository boundary location.

### `data-access/`

1. Own backend communication, repository implementations, DTO handling, and mappers.
2. Use the shared Axios boundary so auth, locale headers, timeout, and error shaping
   stay consistent.
3. DTO-to-domain and domain-to-DTO mapping belongs here, not in UI files.
4. Treat `src/shared/api/orval/*` as generated code. Do not hand-edit it.
5. Run `npm run orval:gen-api` only when the backend contract changes.

### `application/`

1. Expose feature queries, mutations, keys, and orchestration hooks.
2. Keep cache key design and fetching concerns here instead of page components.
3. This repo primarily uses SWR. When touching an existing module, extend its current
   SWR pattern instead of introducing another fetching style into the same feature.
4. Global SWR defaults live in `src/shared/services/configuration/SWRConfiguration.tsx`.
5. Inside a module, `queries.ts` and `mutations.ts` are the default single entry points.

### `ui/`

1. Keep UI files focused on rendering and interaction.
2. `*Page.tsx` files should stay orchestration-oriented and compose smaller pieces.
3. Extract heavy tables, dialogs, cards, and side panels into dedicated components.
4. UI files must not call Axios clients, Orval endpoints, or raw transport helpers directly.
5. All user-facing text must go through i18n.
6. Reusable UI that is shared only within one module belongs in `ui/shared`.

## Data Flow Rules

Use this direction by default:

1. `ui -> application -> repository -> api client -> backend`
2. `backend DTO -> mapper -> domain/entity -> ui`
3. `ui intent -> application payload -> mapper/repository -> backend DTO`

If a file skips one of these boundaries, there should be a clear reason.

## Routing and Localization

1. Do not hardcode route strings across modules. Reuse `src/app/routes/resources.ts`.
2. Route pages should remain lazy-loaded from `src/app/routes/router.tsx`.
3. Keep route `handle.titleKey` aligned with translation keys.
4. When adding or changing copy, update all supported locales under:
   `src/app/locales/langs/en`, `src/app/locales/langs/ru`, and `src/app/locales/langs/uz`.
5. Keep locale persistence and backend language syncing inside the existing settings
   and preferences flow. Do not add parallel locale state management.

## Placement Rules

1. Keep page-specific code inside that page folder under `ui/pages/<PageName>/`.
2. Keep module-specific reusable code inside `ui/shared`.
3. Move code to `src/shared/*` only after it is clearly reused across modules or by the app shell.
4. Keep business contracts and entities inside `domain`, not inside UI or application files.
5. Avoid speculative abstractions and global helpers for single-use cases.

## UI and Styling Rules

1. Reuse the existing theme, settings, and vision-mode infrastructure from `src/app/theme`
   and `src/app/providers`.
2. Import UI primitives from `@mui/material`. Importing from `@mui/system` is restricted.
3. Prefer existing shared components before creating new wrappers around common MUI patterns.
4. Preserve responsive behavior on desktop and mobile.
5. Make loading, empty, and error states explicit for async screens.

## Import and Naming Conventions

1. Prefer path-alias imports such as `app/...`, `modules/...`, and `shared/...`
   over long relative imports when crossing folders.
2. Inside modules, follow the standard names from the target structure:
   `keys.ts`, `queries.ts`, `mutations.ts`, `*.repository.ts`,
   `<module>.repository.impl.ts`, `*.types.ts`, `*.enums.ts`, and `index.ts` barrels.
3. Keep import order compatible with the existing Prettier configuration instead of
   creating style-only churn.
4. Do not rename major folders or move modules around without a repo-wide reason.

## Verification

1. There is no standard test script in this package today.
2. At minimum, run `npm run lint` for changed frontend code.
3. Run `npm run build` when changes touch routing, providers, theme, shared API
   boundaries, or broad shared UI.
4. Run `npm run pretty` only when formatting drift exists. Avoid unrelated formatting-only diffs.

## Anti-Patterns to Avoid

1. Fat page files that mix rendering, fetching, DTO mapping, and mutation logic.
2. UI components importing Axios clients, Orval endpoints, or raw response shapes directly.
3. Hardcoded route strings or hardcoded user-facing copy.
4. Hand-editing generated files under `src/shared/api/orval`.
5. Mixing SWR, React Query, and ad hoc fetch logic inside one feature without an explicit migration plan.
6. Moving module-specific code into `src/shared` too early.
7. Creating ad hoc module folder layouts that do not match the standard module structure.
